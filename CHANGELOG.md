# Changelog

## v0.8.2

Only the daemon changed: a 0.8.2 daemon works with the 0.8.0 or 0.8.1 node helper, so upgrading the PBP host is enough (upgrading the node too does no harm). Configs need no change. Upgrade so that the node install line `pbp setup` prints works again: on 0.8.1 and earlier it downloads from the Gitea release page, which is now private.

- **Releases are published on GitHub**. Development stays on a private Gitea instance; every release, from `v0.2.0-rc.1` on, is also on the GitHub mirror, [Breadth-Security/Proxmox-Backup-Proofing](https://github.com/Breadth-Security/Proxmox-Backup-Proofing/releases), with the same files and `SHA256SUMS.sig`. Every release's description, on Gitea and on GitHub, now carries a "Signed release" note: the key's fingerprint and the command to verify it. The node install line `pbp setup` prints, the docs and the package's homepage now point there. GitHub serves a `~` in a file name as `.`, so the install line fetches a pre-release's package under that name and saves it under the signed one. Commits and tags signed with the release key show as Verified on GitHub.
- **`git tag -v` verifies with `allowed_signers`.** The file listed the key for release files before the key for git, and git stops at the first line with the key, so checking a signed tag or commit failed with "key is not permitted for use in signature namespace git". The git line now comes first; checking release files is unchanged.
- **SLSA provenance on GitHub.** Each release tag also runs the OpenSSF SLSA Go builder on the GitHub mirror, which builds pbp for `amd64` and `arm64` with the same flags as the release and signs SLSA build provenance for it (`slsa-verifier` checks it). The binaries and provenance stay on the workflow run; the release's files are unchanged. The mirror also has a security policy (`SECURITY.md`, private vulnerability reporting) and contribution notes (`CONTRIBUTING.md`).

## v0.8.0

**Upgrade both sides, and reinstall the notification templates**: the notification has a new section, whose data key a 0.7 node helper refuses, so this is a minor release (0.8): the daemon and the helper must share major.minor, and a 0.8 daemon's preflight refuses a 0.7 helper instead of every notification failing. Run the `pbp node setup` line again after upgrading (or `pbp node install-templates`).

- **Previously proven guests get their own section in the notification**. Guests skipped because their newest backup is already proven are no longer listed under SKIPPED but under ☑️ PREVIOUSLY PROVEN, above ✅ PROVEN. Both sections list one guest per line with its name (`VM110: db01`), containers first, then by VMID. The name of a guest that is not restored comes from the node's guest list, or from its backup's notes line when the guest is gone.
- **The backup's comment starts with the guest's name again**. vzdump writes the guest's name as the first line of a backup's notes, which PVE and PBS show as the comment and search on. PBP put its verdict line first, pushing the name out of the comment, so a search by name no longer found proofed backups. The line now reads `db01 · PBP PROVEN 2026-10-19 02:14 · …`, with the name from the backed-up config (or `VM105` without one); a first line that was just the name is replaced by it instead of repeated. Each run rewrites lines PBP 0.5 to 0.7 wrote the same way, keeping their verdict, on every backup of a guest, not only the newest (excluded guests' notes are left alone), up to 100 backups per run after the proofs. See [Backup notes](docs/operating.md#backup-notes).

## v0.7.0

**Upgrade both sides, and reinstall the notification templates.** The notification carries two new data keys (the severity marker and the counts line), which a 0.6 node helper refuses; the daemon and the helper must share major.minor, so a 0.7 daemon's preflight refuses a 0.6 helper. Follow [Upgrading](docs/upgrading.md), then run the `pbp node setup` line again (or `pbp node install-templates` as root on the node); preflight says so if the templates are stale. Configs need no change.

- **Plain verdict reasons**. A privileged container now ends `ERROR` before any restore with `PBP cannot restore privileged containers`, pointing to the options (convert it to unprivileged, exclude it, or grant `Sys.Modify`) in [Guests PBP cannot proof](docs/security.md#guests-pbp-cannot-proof); it used to fail on PVE's 403 with the temporary VMID in the reason. Every reason in the notes and notifications now leaves out the temporary VMID and PVE's API internals, names the missing privilege when PVE refused a step, and points to the guest's log for the detail. Check names read `postgresql (command pg_isready -q)` instead of `postgresql:commands:pg_isready -q`. A VM without an agent says whether the agent is not enabled or did not answer, and what to do ([VMs and the guest agent](docs/checks.md#vms-and-the-guest-agent)).
- **Run summary at a glance.** The run's counts are on their own line, with markers: ✅ proven, ☑️ previously proven (a backup an earlier run proved, which used to count as skipped), ❌ failed, ⚠️ error or booted, ⏭️ skipped, in `run.log`, the service log and the notification. The notification's subject leads with the run's severity marker, and its sections carry the same markers.
- Maintenance: `golang.org/x/crypto` 0.58.0 and `golang.org/x/sys` 0.49.0; the Docker image is now built on `distroless/static-debian13` (Debian 13, was 12); CI uses `actions/checkout` and `actions/setup-go` v7 (Node 24, was Node 20) and Trivy 0.76.1.

## v0.6.1

Only the daemon changed: a 0.6.1 daemon works with the 0.6.0 node helper, so upgrading the PBP host is enough (upgrading the node too does no harm). Configs need no change.

- **Per-guest ignore lists**. A `checks.guests` entry can now carry `ignore_units` and `windows_ignore_services`, which add to the global lists for the guests it matches (by VMID, name or tag) only: a unit that fails by design on one guest, such as a driver loader in a container, no longer has to be ignored on every guest. See [The ignore list](docs/checks.md#the-ignore-list).
- **A drive the backup does not hold is removed from the copy, not left pointing at production**. PVE's restore rewrites only the drives in the backup and keeps every other drive line as it is, so a restored copy could name a production volume: on pve1, VM137 (SeaBIOS with a leftover `efidisk0` that vzdump skips) pointed at its production EFI disk. 0.6.0's disk check refused to start such a copy, so VM137 ended `ERROR` every night. Removing a drive from the copy needs `VM.Config.Disk`, which PBP's role does not include, and 0.6.0's removal of raw host disks needed it too (it failed with a 403). PBP now checks its token's rights first: with `VM.Config.Disk` (granted on `/vms` to `pbp@pve` and its token by the admin, see [Security](docs/security.md#the-api-token)) it removes such drives (the guest's log lists them as not covered by the proof), so the proof goes on; without it the guest ends `ERROR` before anything changes, naming the drives and both fixes (remove them from the original guest, or grant the right). The default role is unchanged.

## v0.6.0

This release carries the rest of the whole-codebase review (#21): the Minor findings in #50–#57, and the refusal to run as root (#63).

**Upgrade both sides.** The daemon and the node helper must share major.minor, so a 0.5 helper does not work with a 0.6 daemon, and the helper itself changed (notify accepts only PBP's own fields; the audit log records more): follow [Upgrading](docs/upgrading.md). The notification templates are unchanged. Check before upgrading:

- **TLS config:** a hand-edited `config.yaml` with both `target.api.tls_fingerprint` and `target.api.ca_file`, or a fingerprint that is not 64 hex digits, no longer loads (the daemon exits 78); configs `pbp setup` wrote are fine.
- **Docker:** the binary moved to `/usr/local/bin/pbp` (on the `PATH`, so `docker compose exec pbp pbp …` now works). If your own compose file overrides the `healthcheck` or `entrypoint` with `/pbp`, change it.
- **Run PBP commands as the service user.** `pbp check`, `pbp run` and `pbp daemon` refuse to run as root when the state or log directory belongs to `pbp`; use `sudo -u pbp …` as the docs show.

- Tests: the daemon's scheduling tests use an injected clock instead of real seconds; the VMID-sharing test makes jobs really overlap; the release workflow runs the package-script tests; the deb layout's key mode is pinned; the fake node helper fails requests it has no handler for; the node end-to-end test also tries remote and agent forwarding and `SetEnv`; every job, run and janitor test checks that only the proofed backup's attributes are written.
- **The node helper accepts only what PBP sends**. A notify request may carry only the `type` and `hostname` fields and the data keys PBP's templates use, so a stolen key can no longer shape notifications to hit other matchers. The audit log now records, for each guest command, its name, argument count, exit code and time taken (never its arguments), so a key compromise can be reconstructed. A notification too large even after shortening its lists is sent with the essentials and a pointer to the run log, never dropped.
- **Setup hardening**. `pbp setup` now tightens the secrets directory, the private key and the token file to the right mode and owner on every run (a key or token an older or manual install left readable stayed that way). When the node rejects this host's token secret (401), it prints the `--rotate-token` line instead of asking for a reply that cannot help. In the one-shell flow on a node, a token secret created before a later failure is saved to the token file, never shown. `pbp node setup` shows text from files the `pbp` user controls with control characters escaped, warns about a `privsep 0` token even without a token flag, and warns about sshd `Match` blocks on an address or host (its key-source check only sees localhost). `pbp node uninstall --remove-token` names the other tokens of `pbp@pve` and the other users' `PBPProofer` grants that go with it. `apt purge` removes setup's sudo rule, and removing the package warns that the PVE user and token stay.
- **API client robustness**. Waiting for a PVE task now rides out about two minutes of failed polls (was about 30 seconds), enough for a `pveproxy` restart, and a reply without a task status counts as a failed poll instead of "still running" forever. An unreachable node fails within 10 seconds instead of after the 5-minute request timeout, redirects are not followed, and a long PVE error message is cut to 1 KiB. The config now refuses `tls_fingerprint` and `ca_file` set together (the CA file was silently ignored) and a fingerprint that is not 64 hex digits. **Upgrade note:** a hand-edited config with both set, or with a malformed fingerprint, stops loading (the daemon exits 78) until you remove one or fix it; configs `pbp setup` wrote are not affected.
- **Probing: fewer verdicts for the wrong reason**. A service whose failure is traced to something not in the backup no longer fails its profile check (the docs' own `postgresql` on an excluded disk example ended `FAILED` on `pg_isready`). A guest whose root is read-only by design can say so with `allow_readonly_root: true` in `checks.guests`. The no-nesting rule applies only to unprivileged containers, names checks that failed too, and follows a socket's `Triggers=`. A Gentoo container running systemd is judged by systemd instead of ending `BOOTED`. A timeout while reading `/proc` (the fallback for a missing `findmnt` or `ss`) is `ERROR`, not `FAILED`.
- Control characters in guest output (a command's stderr, a Windows event message) are escaped in the log files (`\x1b`), so viewing a log cannot run terminal escapes or rewrite lines.
- **The scheduler is sturdier**. A scheduled run that finds the run lock held by another `pbp` command (a `pbp check` at 02:00, say) now waits for it for up to 15 minutes instead of losing the night's run. Runs follow the wall clock: a clock step (a late NTP sync on a VM) no longer starts a run early or twice, and a suspend or forward step starts it within a minute. A schedule that never fires (`0 0 30 2 *`) is refused when the config loads (the daemon exits 78) instead of restarting every 30 seconds while health said ok.
- **Health and notifications in edge cases**. `pbp health` reads the schedule in the daemon's time zone (the daemon records its `TZ` when it starts), so a `TZ` set only on the service no longer gives false "scheduled run missed". A run whose state file cannot be opened now sends a notification (`run not started: state store: …`) instead of failing silently. A run that is restoring past its overrun limit is not reported as overrun before 24 hours, since restores have no timeout of their own.
- **Docker: `docker compose exec pbp pbp …` works**. The image kept the binary at `/pbp`, which is not on the image's `PATH`, so the documented `docker compose exec pbp pbp check` (and `run`, `health`) failed with "executable file not found". It is now `/usr/local/bin/pbp`.
- **Safety: a VM's raw disk passthrough is removed from the copy, and the copy may boot only from its own volumes**. A drive such as `scsi1: /dev/disk/by-id/…` is not in the backup, and PVE's restore keeps its line as it is, so the copy booted with the production disk attached. PBP now removes it like other host passthrough (listed under "not covered by backup"), and before starting checks that every disk is a volume of the temporary guest (or a CD-ROM); anything else ends `ERROR` with the guest never started.
- **The janitor no longer gets stuck**. A crash after PBS refused to protect a backup left a record asking to unprotect it, which PBS refused every night; a leftover of a VM backed up without a `name` could never be recognised. Both stopped every later run at preflight. The refusal is now recorded at once, and a nameless leftover is recognised by its NICs' MAC addresses. A `pbp`-tagged guest in the range on another cluster node is now reported (and left alone) instead of blocking the janitor.
- `pbp check` checks the helper's out-of-range refusal with a VMID no guest uses, so even a broken helper never runs the check in a real guest; and a guest that is gone and whose backup config cannot be read no longer gets an `ERROR` line in its notes when tag exclusions are configured, since that config might have excluded it.
- **`pbp check`, `pbp run` and `pbp daemon` refuse to run as root when the state or log directory belongs to the service user**. Run as root (for example `sudo pbp check` on a `.deb` host), they rewrote `state.json`, the run lock and run log folders as root, and the service, running as `pbp`, could no longer read its own state: its next run stopped with `permission denied`. They now refuse before writing anything and give the command to run instead (`sudo -u pbp pbp … --config …`). A root-only install, whose directories belong to root, is not affected; `pbp health` and `pbp version` only read and work as root. If an earlier version left root-owned files behind, see [Troubleshooting](docs/troubleshooting.md).

## v0.5.0

This release carries the fixes from the whole-codebase review: safety (#46), verdict correctness (#47), robustness (#48), and setup, docs and tests (#49).

**Upgrade both sides.** The daemon and the node helper must share major.minor, so a 0.4 helper does not work with a 0.5 daemon, and the helper itself changed (it now caps a guest command's output): follow [Upgrading](docs/upgrading.md). The notification templates are unchanged. If you run PBP with Docker Compose from your own `docker-compose.yml`, raise `stop_grace_period` to `25m` as in this release's file, so a stopped PBP can finish its proofs, tear down and notify. Existing configs need no change; your ignore lists now add to the built-in ones (see below).

- **`pbp node setup --replace` fixes an `authorized_keys` with the right line but the wrong owner or mode**. Setup reported the file as differing but left it as it was, so the self-test failed on every rerun and a file writable by `pbp` stayed writable (letting a process running as `pbp` rewrite its own forced command). It is now rewritten with the right owner and mode.
- Docs: [security.md](docs/security.md) now says plainly that a stolen PBP SSH key reaches root inside every proof container while it runs, which is a copy of production data, and how to protect the key accordingly; `restore.max_run_duration` is described as what it is, a point after which no new proof starts (proofs in progress still finish), not a cap on run length.

- **A guest's output cannot run PBP out of memory or lose the run's notification**. The output of a command in a proof container was buffered in full, so a hostile or broken guest (a copy of a compromised container, or a chatty check) could stream gigabytes and get PBP killed mid-run; a reason naming thousands of units could push the notification past the node helper's 1 MiB limit, losing the notification for the whole run. Now the node helper passes on at most 8 MiB per stream and kills a command that prints more (the guest ends `ERROR`), and PBP reads at most 16 MiB per stream whatever the node sends. A reason names at most 10 units (`… and 40 more`; all are in the guest's log), each check's detail and each notification line are clipped, the boot log keeps its newest 256 KiB, and a notification that would still be too big lists the first problems and points to the run log. A background process a guest command leaves holding its output no longer keeps the command running past 5 seconds.
- **A dead SSH connection no longer hangs a run**. If the connection to the node died silently while idle (a NAT or firewall dropping it during a long restore), the next check, bridge read or notification waited about 15 minutes for TCP to give up, ignoring its own deadline. PBP now sends SSH keepalives every 15 seconds and drops the connection when three in a row go unanswered (like OpenSSH's `ServerAliveCountMax`), so the next command reconnects; opening a session or starting a command gives up at the caller's deadline, and a check the node never answered ends `ERROR`, not `check timed out`.

- **Windows: broken delayed-start services are caught, and a failing service query is retried**. Delayed-start automatic services were never checked, so a broken one could not fail the guest; now they count when they actually failed (an error exit code or a failure event), not when they stopped cleanly. Since Windows starts them about two minutes after boot, PBP keeps checking for up to 4 minutes while one has not started yet. The Service Control Manager event shown for a stopped service is now matched on the service's name exactly, so a service whose name is part of another's (`Spooler`, `Print Spooler Helper`) is no longer given the other's event. A PowerShell timeout or non-zero exit was `FAILED` at once; it is now retried within the settle wait, and `ERROR` if it still fails at the end.
- **OpenRC guests: a service that failed to start fails the guest, and the read-only-root and per-guest checks apply**. `rc-status --crashed` lists only daemons that died after starting; a service that never started shows as `stopped` in its runlevel (seen on Alpine 3.24) and was missed, and OpenRC guests skipped the read-only-root and per-guest checks. PBP now reads `rc-status --format ini` (falling back to `--crashed` on an OpenRC without it), runs the read-only-root check, and runs per-guest ports, commands and services (with `rc-service`). The built-in service profiles stay systemd-only.
- **A crash-looping service makes the guest `FAILED`**. A service that keeps crashing under `Restart=always` never reaches "failed" (systemd keeps restarting it), so the guest could be `PROVEN`. A service in `auto-restart` that restarted after a failed run, or 3 times or more after clean exits, now counts as a failed unit (subject to `checks.ignore_units` and the "not covered by backup" tracing).
- **A read-only root is never missed, and port checks work without `ss`**. If `findmnt` was missing or failed, the read-only-root check was silently skipped, so a guest with a read-only root could be `PROVEN`; if `ss` was missing, every port check failed. PBP now falls back to `/proc/self/mounts` and `/proc/net/tcp`/`tcp6`, and if those cannot be read either, the guest is `ERROR`, never passed or failed on a guess.
- **Guests with systemd older than 240 are judged correctly**. `systemctl is-system-running --wait` is an unknown option before systemd 232 (RHEL/CentOS 7), so a healthy guest ended `FAILED · system state: `, and systemd 232 to 239 (Ubuntu 18.04 ships 237) accept it but return at once, so a guest still booting ended `FAILED · system state: starting`. PBP now polls the state instead in both cases.
- **A command missing in a VM is handled like in a container**. The guest agent reports a command that does not exist as an error, not as exit code 127, so PBP's fallbacks for a missing command never applied to VMs, and a Linux VM without `systemctl` ended `ERROR`. That error is now treated as exit 127.
- **A failed restore is `FAILED` only for real backup damage**. Any restore error PBP did not recognise as the node's fault was `FAILED`, blaming the backup: out of space on LVM, out of memory, HTTP 400/404/502/503, a dropped connection, or the root-only bind-mount refusal. Now only known damage (corrupt or missing chunks, including a chunk file missing from the datastore, checksum or digest mismatches, data that cannot be decoded) is `FAILED`; everything else is `ERROR`.
- **An interrupted run is reported and cleaned up**. A run cut short by PBP being killed or crashing stayed recorded as running: `pbp health` said ok for a day, no notification was sent, and its leftover guests waited for the next run's janitor. Now the daemon, when it starts, marks such a run as an error (so `pbp health` reports it), sends a notification, and runs the janitor at once; a run that finds an earlier one still marked running (for example a killed `pbp run`) does the same marking and lists it in its summary.
- **A run on demand cleans up when its session drops**. `pbp run` ended on SIGHUP (an SSH session dropping) without tearing its guest down. SIGHUP now ends any PBP command except the node helper gracefully, like SIGTERM (unless it was started under `nohup`, which keeps it running), and a closed stdout no longer kills it on its next write. Under Docker, a `docker compose exec` run still ends with the container: let it finish before stopping PBP.
- **Stopping PBP no longer starts new proofs**. On SIGTERM the daemon kept restoring further guests for its 10-minute grace, then cancelled them and wrote `ERROR … cancelled` into their backups' notes. Now no further proof starts once a stop is requested (the rest are `SKIPPED · PBP stopping`, with no note, so a run stopped part-way is reported with severity `warning`), and proofs in flight get the grace to finish; one still running when the grace ends is cancelled as before. The systemd `TimeoutStopSec` and the Compose `stop_grace_period` are now 25 minutes (were 11), so teardown and the notification can complete after the grace; keep them when you customise either.
- **Safety: a VMID whose teardown failed is not reused in the same run**. When a proof's unprotect failed, its VMID was freed and could go to the next guest, overwriting the record the janitor needs, so that backup stayed protected for good. The VMID now stays reserved while its record remains. (Across runs this could not happen: a record the janitor cannot finish stops the next run at preflight.)
- **Safety: PBP reads a backup's `protected` flag just before protecting it**, not from the run's listing, which may be hours old. A backup an admin protected during the run was unprotected at teardown, exposing it to pruning. If the flag cannot be read, the proof ends `ERROR` before anything changes.
- **Safety: a restored copy is created with `onboot` off** (code review). The copy kept the backup's `onboot: 1` and its production NICs until PBP sanitized it, so if PBP stopped or crashed mid-proof, or sanitizing and destroying both failed, a node reboot before the next run could autostart a copy of a production server on the production network. PBP now passes `onboot=0` with the restore request itself, and clears it again in its first write after the restore.
- **Windows: why a service is stopped**. For each automatic service that makes a Windows guest `FAILED`, the guest's log file now says why it stopped: the newest Service Control Manager event since boot that names it, and its exit code (large codes in hex), for example `Bonjour Service stopped: event 7024: … (service-specific exit code 0xFFFFFFFF)`. It is read in the same PowerShell call as the service list, so it costs no extra time.
- Docs: [Proofing on your disaster-recovery standby](docs/dedicated-node.md#proofing-on-your-disaster-recovery-standby) recommends proofing on the hardware your disaster recovery plan would restore to, and covers cold spares that are woken for the run, standbys at another site, and the capacity proofing borrows.
- `WslInstaller` is on the built-in Windows ignore list: on Windows 11 it checks or installs WSL at boot, then exits, so "automatic but stopped" is its normal state (it made VM115 `FAILED` in testing).
- **Your ignore lists now add to PBP's built-in ones.** `checks.ignore_units` and `checks.windows_ignore_services` used to replace the built-in lists, and `pbp setup` wrote a full copy of them into `config.yaml`, so a new built-in entry never reached an existing install. Now your entries are added to the built-in lists (duplicates dropped; Windows names compared ignoring case), and `pbp setup` writes empty lists for your additions. Existing configs need no change: their copied entries simply overlap. Set `checks.use_default_ignores: false` to use exactly your own lists, as before. If you had removed a built-in entry by leaving it out of your list, set that option.
- **A slow guest agent no longer ends a proof**. When the QEMU guest agent was slow to answer a status poll (`qga command 'guest-exec-status' failed - got timeout`, seen on a Windows VM shortly after boot), the proof ended `ERROR · probe transport error`. PBP now polls again, within the command's own time limit (`checks.command_timeout`); other agent errors still end the command at once.
- The guest log no longer shows a spurious `verdict now` line, or a verdict line split over several lines, when the reason contains line breaks.
- **Proofing on a dedicated node**: a new guide, [docs/dedicated-node.md](docs/dedicated-node.md), for restoring and booting the proof copies on a separate Proxmox host, tested with a standalone PVE 9.2 node and PBS 4.2. When PBS refuses to protect a backup because the node's PBS storage lacks the rights (for example a read-only token), the proof now ends `ERROR · protect backup: PBS refused: …`, naming the rights needed, and PBP no longer tries to undo the refused change or leaves a job for the janitor that would fail on every run.
- **Exclude guests from proofing**. `selection.exclude.guests` takes VMIDs (`104`), labels for one kind (`VM104`, `CT109`) and ranges (`900-999`); `selection.exclude.tags` excludes guests whose live or backed-up config carries a tag. An excluded guest is `SKIPPED · excluded by config (<rule>)` before anything is reserved or restored, its backup is not touched, and the skip does not raise the run's severity. `pbp run --guest N` refuses an excluded guest. See [Excluding guests](docs/operating.md#excluding-guests).

## v0.4.0

**Upgrade both sides.** The daemon and the node helper must share major.minor, so a 0.3 helper does not work with a 0.4 daemon: follow [Upgrading](docs/upgrading.md). Running the `pbp node setup` line also installs this version's notification templates, which changed; until then preflight reports `notification templates on the node: … differs from this version's`.

- **Unprivileged containers without nesting are no longer `FAILED`**. Without `features: nesting=1`, systemd cannot start sandboxed units (`226/NAMESPACE`) or its own API mounts, in the production container as in the copy, so the backup was blamed for the container's configuration. Such a container now ends `BOOTED`, naming the units and recommending `nesting=1`; any other failed unit still makes it `FAILED`.
- **Containers with raw `lxc.*` lines end `ERROR` before restoring**. PVE drops those lines when PBP's token restores, so the copy ran under a different configuration than the guest (seen with `lxc.apparmor.profile: unconfined`) and could fail for no fault of the backup. PBP now reads them from the backed-up config and reports `raw lxc config (…) needs root@pam to restore`, as the docs already said.
- **Containers using DHCP and IPv6 autoconfiguration are proofed again**. A container with `ip=dhcp,ip6=auto` never finished booting on the isolated bridge: its ifupdown2 network service waits for an IPv6 answer that never comes, so the proof ended `ERROR` (`guest still starting after 4m30s`). PBP now sets a container's `ip=dhcp` and `ip6=auto`/`ip6=dhcp` to `manual` when it makes the restored copy safe; static addresses are kept, and VMs are unchanged. Containers with `ip=dhcp` alone also boot about 85 seconds faster. When a guest still does not finish booting, the reason names the units it is waiting on.
- **Run logs and the notification are easier to read**. Each run now writes a folder under `logging.dir` (for example `2026-10-21_02-00-00_schedule/`) with `run.log` and one `VM102.log` / `CT101.log` per guest, as readable text instead of JSON, with a line for every step as it happens. `logging.retain_runs` counts folders; old `run-*.log` files count toward it until they age out. A failed PVE task now shows only its error line as the reason, with the task log's tail in the guest's file. The notification leads with the problems, has a short subject (`PBP pve1: 9 failed, 9 error · 13 proven`), names guests `VM102` / `CT101` throughout, and gives the log folder. **After upgrading, reinstall the node's notification templates** (`pbp node install-templates`, or the `pbp node setup` line); preflight reports outdated ones.
- Backups of VM and container templates (`template: 1` in the config stored in the backup) are skipped as `template (not bootable)` before anything is reserved or restored, instead of being proofed and failing to start. The backup's notes and `protected` flag are not touched, and the skip does not raise the run's severity.

## v0.3.0

**Guided setup.** Two commands now do what the README's "Setup" section used to describe step by step. See [docs/setup.md](docs/setup.md).

- `pbp setup` on the PBP host (Docker: a one-shot `docker run`, see [docs/setup.md](docs/setup.md#3-run-pbp-setup-on-the-pbp-host) for the exact command; `.deb` hosts: `sudo pbp setup --deb`) asks a few questions, writes `config.yaml` from `config.example.yaml` with its comments, creates the SSH key, and prints two lines to run on the node: the checksum-verified install of the matching `.deb`, and `pbp node setup`. It then reads the node's reply (without echoing it) and writes `known_hosts`, the token secret, `target.node` and `target.api.tls_fingerprint`, and runs the check. Files get the owners and modes the README already required.
- `pbp node setup`, as root in an interactive terminal on the node, checks the node, shows a plan, asks, and then sets up the helper exactly as the manual steps do (`node.yaml`, the `pbp` shell, the forced-command key, the sudo rule, the notification templates), plus the API role, user, privilege-separated token and ACLs (`--create-token`). It proves the result through the real sudo path and prints a reply block with the node's host key, the API certificate fingerprint and, once, the token secret. Options: `--dry-run`, `--yes`, `--replace` (a differing file is copied to `<file>.pbp-backup-<YYYYMMDDTHHMMSS>` first; without it setup stops), `--rotate-token`. It refuses to run from an SSH forced command (`SSH_ORIGINAL_COMMAND` set), through the `pbp` sudo rule, or without a terminal, and never creates the bridge, reloads networking, or touches root's `authorized_keys`, `sshd_config` or any guest. It needs `sudo` (Proxmox VE does not install it; the `.deb` now recommends it), and stops, without changing anything, if sshd would read `pbp`'s keys from anywhere but `/var/lib/pbp/.ssh/authorized_keys` (for example an `authorized_keys2`, another `AuthorizedKeysFile`, an `AuthorizedKeysCommand`, or an SSH user CA via `TrustedUserCAKeys` or `AuthorizedPrincipalsCommand`) or if that `.ssh` holds other files.
- Both print `setup has already been completed` when there is nothing to do.
- `pbp`'s home, `/var/lib/pbp`, now belongs to root (`0755`): the package makes it so on install and upgrade, so `pbp` cannot move or replace the `.ssh` directory that holds its forced-command key. The daemon's state moved to `/var/lib/pbp/state` (`PBP_STATE_DIR`'s default; owned by `pbp` on a `.deb` host, by uid 65532 in the image). `pbp node setup` refuses a home that is not root's.
- `pbp node setup` warns when `pbp@pve` or its tokens have permissions beyond PBP's role and paths (another role or path, a group, a second token), and re-applies an ACL entry that does not propagate.
- `sudo pbp setup --deb` on a Proxmox VE node sets the node up in the same run: it offers `127.0.0.1` as the node address, asks before running `pbp node setup`'s checks and plan, and passes the reply internally (no second shell, nothing pasted, the token secret never shown). It offers to replace an existing token it has no secret for.
- `pbp setup` checks that the node address reaches the node that printed the reply (by the SSH host key, without logging in) before writing anything, and names the address, what it resolves to and the node's own addresses when it does not. The node's reply now carries those addresses.
- `pbp check`'s "pve api" step makes a real request.
- The daemon exits 78 on a config it cannot use, and `pbp.service` does not restart on it.
- `--rotate-token`'s plan and docs say that the new token is granted only the paths of that run.
- `pbp node uninstall` removes the sudo rule and the key first, then `node.yaml`, and sets the `pbp` shell back to `nologin`. `--remove-token` also removes the token, ACLs, user and role. `--dry-run` and `--yes` as for setup.
- `docker-compose.yml` reads the time zone from `.env` (`TZ: ${TZ:-Europe/London}`), which `pbp setup` writes; `.env` is git-ignored.
- The `.deb` no longer starts `pbp.service` from its postinst: an install only enables it (start it once with `systemctl start pbp`), and an upgrade restarts it only if it is running. Before, an upgrade started an enabled, stopped service whenever `/etc/pbp/config.yaml` existed, which on a node could start a daemon from a stray config. `pbp node setup` warns when the node also runs a PBP daemon.
- The manual steps remain, unchanged in substance, in [docs/manual-setup.md](docs/manual-setup.md).
- The README is now a short overview; the setup, operating, checks, troubleshooting, upgrading and development sections moved to `docs/`, which the `.deb` and the tarballs ship next to the README. Messages that pointed at README "Node setup" now say `see docs/setup.md`.

## v0.2.0

**Breaking change: PBP no longer uses root SSH.** The daemon talks to a restricted `pbp node` helper on the PVE node, through an SSH forced command for the unprivileged `pbp` user and one sudo rule. The helper can run `pct exec` only in tagged containers inside the configured VMID range, report the isolated bridge's state, send `pbp` notifications and print its config. See [docs/manual-setup.md](docs/manual-setup.md#node-setup).

Behaviour changes:

- `target.ssh.user` defaults to `pbp`. `root` is rejected by config validation.
- The node needs `/etc/pbp/node.yaml` (`vmid_range`, `bridge`, optional `request_timeout`, default 15m). `pbp check` and preflight fail if it differs from `target.vmid_range` and `target.bridge`.
- The daemon and the helper must share major.minor (`0.2.x` with `0.2.y`). A `dev` build is compatible only with a `dev` build.
- A Docker build without `--build-arg VERSION` (including `docker compose build`) is stamped from the new top-level `VERSION` file instead of `dev`. The release workflow fails a tag whose version disagrees with it.
- PBP no longer installs the notification templates itself. Run `pbp node install-templates` as root on the node; preflight only checks them.
- `pbp check` has new steps: node helper version, config, `request_timeout` and refusal.
- The `.deb` is unchanged for daemon-only hosts (the `pbp` user keeps the `nologin` shell). On a node, `apt purge pbp` deletes the `pbp` user and PBP's access.
- Integration tests use a separate test-only admin key (`PBP_IT_ADMIN_SSH_KEY`); see `test/integration/README.md`.
