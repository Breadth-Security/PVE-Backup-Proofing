# Changelog

## Unreleased

- **A guest's output cannot run PBP out of memory or lose the run's notification** ([#48](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/48)). The output of a command in a proof container was buffered in full, so a hostile or broken guest (a copy of a compromised container, or a chatty check) could stream gigabytes and get PBP killed mid-run; a reason naming thousands of units could push the notification past the node helper's 1 MiB limit, losing the notification for the whole run. Now the node helper passes on at most 8 MiB per stream and kills a command that prints more (the guest ends `ERROR`), and PBP reads at most 16 MiB per stream whatever the node sends. A reason names at most 10 units (`… and 40 more`; all are in the guest's log), each check's detail and each notification line are clipped, the boot log keeps its newest 256 KiB, and a notification that would still be too big lists the first problems and points to the run log. A background process a guest command leaves holding its output no longer keeps the command running past 5 seconds.
- **A dead SSH connection no longer hangs a run** ([#48](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/48)). If the connection to the node died silently while idle (a NAT or firewall dropping it during a long restore), the next check, bridge read or notification waited about 15 minutes for TCP to give up, ignoring its own deadline. PBP now sends SSH keepalives every 30 seconds and reconnects when one goes unanswered for 15 seconds, and opening a session or starting a command gives up at the caller's deadline.

- **Windows: broken delayed-start services are caught, and a failing service query is retried** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). Delayed-start automatic services were never checked, so a broken one could not fail the guest; now they count when they actually failed (an error exit code or a failure event), not when they stopped cleanly. Since Windows starts them about two minutes after boot, PBP keeps checking for up to 4 minutes while one has not started yet. The Service Control Manager event shown for a stopped service is now matched on the service's name exactly, so a service whose name is part of another's (`Spooler`, `Print Spooler Helper`) is no longer given the other's event. A PowerShell timeout or non-zero exit was `FAILED` at once; it is now retried within the settle wait, and `ERROR` if it still fails at the end.
- **OpenRC guests: a service that failed to start fails the guest, and the read-only-root and per-guest checks apply** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). `rc-status --crashed` lists only daemons that died after starting; a service that never started shows as `stopped` in its runlevel (seen on Alpine 3.24) and was missed, and OpenRC guests skipped the read-only-root and per-guest checks. PBP now reads `rc-status --format ini` (falling back to `--crashed` on an OpenRC without it), runs the read-only-root check, and runs per-guest ports, commands and services (with `rc-service`). The built-in service profiles stay systemd-only.
- **A crash-looping service makes the guest `FAILED`** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). A service that keeps crashing under `Restart=always` never reaches "failed" (systemd keeps restarting it), so the guest could be `PROVEN`. A service in `auto-restart` that restarted after a failed run, or 3 times or more after clean exits, now counts as a failed unit (subject to `checks.ignore_units` and the "not covered by backup" tracing).
- **A read-only root is never missed, and port checks work without `ss`** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). If `findmnt` was missing or failed, the read-only-root check was silently skipped, so a guest with a read-only root could be `PROVEN`; if `ss` was missing, every port check failed. PBP now falls back to `/proc/self/mounts` and `/proc/net/tcp`/`tcp6`, and if those cannot be read either, the guest is `ERROR`, never passed or failed on a guess.
- **Guests with systemd older than 240 are judged correctly** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). `systemctl is-system-running --wait` is an unknown option before systemd 232 (RHEL/CentOS 7), so a healthy guest ended `FAILED · system state: `, and systemd 232 to 239 (Ubuntu 18.04 ships 237) accept it but return at once, so a guest still booting ended `FAILED · system state: starting`. PBP now polls the state instead in both cases.
- **A command missing in a VM is handled like in a container** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). The guest agent reports a command that does not exist as an error, not as exit code 127, so PBP's fallbacks for a missing command never applied to VMs, and a Linux VM without `systemctl` ended `ERROR`. That error is now treated as exit 127.
- **A failed restore is `FAILED` only for real backup damage** ([#47](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/47)). Any restore error PBP did not recognise as the node's fault was `FAILED`, blaming the backup: out of space on LVM, out of memory, HTTP 400/404/502/503, a dropped connection, or the root-only bind-mount refusal. Now only known damage (corrupt or missing chunks, including a chunk file missing from the datastore, checksum or digest mismatches, data that cannot be decoded) is `FAILED`; everything else is `ERROR`.
- **An interrupted run is reported and cleaned up** ([#46](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/46)). A run cut short by PBP being killed or crashing stayed recorded as running: `pbp health` said ok for a day, no notification was sent, and its leftover guests waited for the next run's janitor. Now the daemon, when it starts, marks such a run as an error (so `pbp health` reports it), sends a notification, and runs the janitor at once; a run that finds an earlier one still marked running (for example a killed `pbp run`) does the same marking and lists it in its summary.
- **A run on demand cleans up when its session drops** ([#46](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/46)). `pbp run` ended on SIGHUP (an SSH session dropping) without tearing its guest down. SIGHUP now ends any PBP command except the node helper gracefully, like SIGTERM (unless it was started under `nohup`, which keeps it running), and a closed stdout no longer kills it on its next write. Under Docker, a `docker compose exec` run still ends with the container: let it finish before stopping PBP.
- **Stopping PBP no longer starts new proofs** ([#46](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/46)). On SIGTERM the daemon kept restoring further guests for its 10-minute grace, then cancelled them and wrote `ERROR … cancelled` into their backups' notes. Now no further proof starts once a stop is requested (the rest are `SKIPPED · PBP stopping`, with no note, so a run stopped part-way is reported with severity `warning`), and proofs in flight get the grace to finish; one still running when the grace ends is cancelled as before. The systemd `TimeoutStopSec` and the Compose `stop_grace_period` are now 25 minutes (were 11), so teardown and the notification can complete after the grace; keep them when you customise either.
- **Safety: a VMID whose teardown failed is not reused in the same run** ([#46](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/46)). When a proof's unprotect failed, its VMID was freed and could go to the next guest, overwriting the record the janitor needs, so that backup stayed protected for good. The VMID now stays reserved while its record remains. (Across runs this could not happen: a record the janitor cannot finish stops the next run at preflight.)
- **Safety: PBP reads a backup's `protected` flag just before protecting it**, not from the run's listing, which may be hours old ([#46](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/46)). A backup an admin protected during the run was unprotected at teardown, exposing it to pruning. If the flag cannot be read, the proof ends `ERROR` before anything changes.
- **Safety: a restored copy is created with `onboot` off** (code review, [#46](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/46)). The copy kept the backup's `onboot: 1` and its production NICs until PBP sanitized it, so if PBP stopped or crashed mid-proof, or sanitizing and destroying both failed, a node reboot before the next run could autostart a copy of a production server on the production network. PBP now passes `onboot=0` with the restore request itself, and clears it again in its first write after the restore.
- **Windows: why a service is stopped** ([#44](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/44)). For each automatic service that makes a Windows guest `FAILED`, the guest's log file now says why it stopped: the newest Service Control Manager event since boot that names it, and its exit code (large codes in hex), for example `Bonjour Service stopped: event 7024: … (service-specific exit code 0xFFFFFFFF)`. It is read in the same PowerShell call as the service list, so it costs no extra time.
- Docs: [Proofing on your disaster-recovery standby](docs/dedicated-node.md#proofing-on-your-disaster-recovery-standby) recommends proofing on the hardware your disaster recovery plan would restore to, and covers cold spares that are woken for the run, standbys at another site, and the capacity proofing borrows ([#40](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/40)).
- `WslInstaller` is on the built-in Windows ignore list: on Windows 11 it checks or installs WSL at boot, then exits, so "automatic but stopped" is its normal state (it made VM115 `FAILED` in testing).
- **Your ignore lists now add to PBP's built-in ones.** `checks.ignore_units` and `checks.windows_ignore_services` used to replace the built-in lists, and `pbp setup` wrote a full copy of them into `config.yaml`, so a new built-in entry never reached an existing install. Now your entries are added to the built-in lists (duplicates dropped; Windows names compared ignoring case), and `pbp setup` writes empty lists for your additions. Existing configs need no change: their copied entries simply overlap. Set `checks.use_default_ignores: false` to use exactly your own lists, as before. If you had removed a built-in entry by leaving it out of your list, set that option.
- **A slow guest agent no longer ends a proof** ([#41](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/41)). When the QEMU guest agent was slow to answer a status poll (`qga command 'guest-exec-status' failed - got timeout`, seen on a Windows VM shortly after boot), the proof ended `ERROR · probe transport error`. PBP now polls again, within the command's own time limit (`checks.command_timeout`); other agent errors still end the command at once.
- The guest log no longer shows a spurious `verdict now` line, or a verdict line split over several lines, when the reason contains line breaks ([#42](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/42)).
- **Proofing on a dedicated node** ([#30](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/30)): a new guide, [docs/dedicated-node.md](docs/dedicated-node.md), for restoring and booting the proof copies on a separate Proxmox host, tested with a standalone PVE 9.2 node and PBS 4.2. When PBS refuses to protect a backup because the node's PBS storage lacks the rights (for example a read-only token), the proof now ends `ERROR · protect backup: PBS refused: …`, naming the rights needed, and PBP no longer tries to undo the refused change or leaves a job for the janitor that would fail on every run.
- **Exclude guests from proofing** ([#32](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/32)). `selection.exclude.guests` takes VMIDs (`104`), labels for one kind (`VM104`, `CT109`) and ranges (`900-999`); `selection.exclude.tags` excludes guests whose live or backed-up config carries a tag. An excluded guest is `SKIPPED · excluded by config (<rule>)` before anything is reserved or restored, its backup is not touched, and the skip does not raise the run's severity. `pbp run --guest N` refuses an excluded guest. See [Excluding guests](docs/operating.md#excluding-guests).

## v0.4.0

**Upgrade both sides.** The daemon and the node helper must share major.minor, so a 0.3 helper does not work with a 0.4 daemon: follow [Upgrading](docs/upgrading.md). Running the `pbp node setup` line also installs this version's notification templates, which changed; until then preflight reports `notification templates on the node: … differs from this version's`.

- **Unprivileged containers without nesting are no longer `FAILED`** ([#34](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/34)). Without `features: nesting=1`, systemd cannot start sandboxed units (`226/NAMESPACE`) or its own API mounts, in the production container as in the copy, so the backup was blamed for the container's configuration. Such a container now ends `BOOTED`, naming the units and recommending `nesting=1`; any other failed unit still makes it `FAILED`.
- **Containers with raw `lxc.*` lines end `ERROR` before restoring** ([#34](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/34)). PVE drops those lines when PBP's token restores, so the copy ran under a different configuration than the guest (seen with `lxc.apparmor.profile: unconfined`) and could fail for no fault of the backup. PBP now reads them from the backed-up config and reports `raw lxc config (…) needs root@pam to restore`, as the docs already said.
- **Containers using DHCP and IPv6 autoconfiguration are proofed again** ([#29](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/29)). A container with `ip=dhcp,ip6=auto` never finished booting on the isolated bridge: its ifupdown2 network service waits for an IPv6 answer that never comes, so the proof ended `ERROR` (`guest still starting after 4m30s`). PBP now sets a container's `ip=dhcp` and `ip6=auto`/`ip6=dhcp` to `manual` when it makes the restored copy safe; static addresses are kept, and VMs are unchanged. Containers with `ip=dhcp` alone also boot about 85 seconds faster. When a guest still does not finish booting, the reason names the units it is waiting on.
- **Run logs and the notification are easier to read** ([#26](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/26)). Each run now writes a folder under `logging.dir` (for example `2026-10-21_02-00-00_schedule/`) with `run.log` and one `VM102.log` / `CT101.log` per guest, as readable text instead of JSON, with a line for every step as it happens. `logging.retain_runs` counts folders; old `run-*.log` files count toward it until they age out. A failed PVE task now shows only its error line as the reason, with the task log's tail in the guest's file. The notification leads with the problems, has a short subject (`PBP pve1: 9 failed, 9 error · 13 proven`), names guests `VM102` / `CT101` throughout, and gives the log folder. **After upgrading, reinstall the node's notification templates** (`pbp node install-templates`, or the `pbp node setup` line); preflight reports outdated ones.
- Backups of VM and container templates (`template: 1` in the config stored in the backup) are skipped as `template (not bootable)` before anything is reserved or restored, instead of being proofed and failing to start. The backup's notes and `protected` flag are not touched, and the skip does not raise the run's severity. ([#27](https://git.breadthanalytics.com/tdiana/Proxmox-Backup-Proofing/issues/27))

## v0.3.1

- **Security:** built with Go 1.26.10, which fixes [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) (`crypto/x509` trusted compromised intermediate certificates). PBP verifies the Proxmox API's TLS certificate, so the daemon is affected. Upgrade the PBP host and the node helper together, as for any release ([Upgrading](docs/upgrading.md)).

## v0.3.0

**Guided setup.** Two commands now do what the README's "Setup" section used to describe step by step. See [docs/setup.md](docs/setup.md).

- `pbp setup` on the PBP host (Docker: a one-shot `docker run`, see [docs/setup.md](docs/setup.md#3-run-pbp-setup-on-the-pbp-host) for the exact command; `.deb` hosts: `sudo pbp setup --deb`) asks a few questions, writes `config.yaml` from `config.example.yaml` with its comments, creates the SSH key, and prints two lines to run on the node: the checksum-verified install of the matching `.deb`, and `pbp node setup`. It then reads the node's reply (without echoing it) and writes `known_hosts`, the token secret, `target.node` and `target.api.tls_fingerprint`, and runs the check. Files get the owners and modes the README already required.
- `pbp node setup`, as root in an interactive terminal on the node, checks the node, shows a plan, asks, and then sets up the helper exactly as the manual steps do (`node.yaml`, the `pbp` shell, the forced-command key, the sudo rule, the notification templates), plus the API role, user, privilege-separated token and ACLs (`--create-token`). It proves the result through the real sudo path and prints a reply block with the node's host key, the API certificate fingerprint and, once, the token secret. Options: `--dry-run`, `--yes`, `--replace` (a differing file is copied to `<file>.pbp-backup-<YYYYMMDDTHHMMSS>` first; without it setup stops), `--rotate-token`. It refuses to run from an SSH forced command (`SSH_ORIGINAL_COMMAND` set), through the `pbp` sudo rule, or without a terminal, and never creates the bridge, reloads networking, or touches root's `authorized_keys`, `sshd_config` or any guest. It needs `sudo` (Proxmox VE does not install it; the `.deb` now recommends it), and stops, without changing anything, if sshd would read `pbp`'s keys from anywhere but `/var/lib/pbp/.ssh/authorized_keys` (for example an `authorized_keys2`, another `AuthorizedKeysFile`, an `AuthorizedKeysCommand`, or an SSH user CA via `TrustedUserCAKeys` or `AuthorizedPrincipalsCommand`) or if that `.ssh` holds other files.
- Both print `setup has already been completed` when there is nothing to do.
- `pbp`'s home, `/var/lib/pbp`, now belongs to root (`0755`): the package makes it so on install and upgrade, so `pbp` cannot move or replace the `.ssh` directory that holds its forced-command key. The daemon's state moved to `/var/lib/pbp/state` (`PBP_STATE_DIR`'s default; owned by `pbp` on a `.deb` host, by uid 65532 in the image). `pbp node setup` refuses a home that is not root's.
- `pbp node setup` warns when `pbp@pve` or its tokens have permissions beyond PBP's role and paths (another role or path, a group, a second token), and re-applies an ACL entry that does not propagate.
- `sudo pbp setup --deb` on a Proxmox VE node sets the node up in the same run: it offers `127.0.0.1` as the node address, asks before running `pbp node setup`'s checks and plan, and passes the reply internally (no second shell, nothing pasted, the token secret never shown). It offers to replace an existing token it has no secret for.
- `pbp setup` checks that the node address reaches the node that printed the reply (by the SSH host key, without logging in) before writing anything, and names the address, what it resolves to and the node's own addresses when it does not. The node's reply now carries those addresses.
- `pbp check`'s "pve api" step makes a real request.
- The daemon exits 78 on a config it cannot use, and `pbp.service` does not restart on it.
- `--rotate-token`'s plan and docs say that the new token is granted only the paths of that run.
- `pbp node uninstall` removes the sudo rule and the key first, then `node.yaml`, and sets the `pbp` shell back to `nologin`. `--remove-token` also removes the token, ACLs, user and role. `--dry-run` and `--yes` as for setup.
- `docker-compose.yml` reads the time zone from `.env` (`TZ: ${TZ:-Europe/London}`), which `pbp setup` writes; `.env` is git-ignored.
- The `.deb` no longer starts `pbp.service` from its postinst: an install only enables it (start it once with `systemctl start pbp`), and an upgrade restarts it only if it is running. Before, an upgrade started an enabled, stopped service whenever `/etc/pbp/config.yaml` existed, which on a node could start a daemon from a stray config. `pbp node setup` warns when the node also runs a PBP daemon.
- The manual steps remain, unchanged in substance, in [docs/manual-setup.md](docs/manual-setup.md).
- The README is now a short overview; the setup, operating, checks, troubleshooting, upgrading and development sections moved to `docs/`, which the `.deb` and the tarballs ship next to the README. Messages that pointed at README "Node setup" now say `see docs/setup.md`.

## v0.2.0

**Breaking change: PBP no longer uses root SSH.** The daemon talks to a restricted `pbp node` helper on the PVE node, through an SSH forced command for the unprivileged `pbp` user and one sudo rule. The helper can run `pct exec` only in tagged containers inside the configured VMID range, report the isolated bridge's state, send `pbp` notifications and print its config. See [docs/manual-setup.md](docs/manual-setup.md#node-setup).

Behaviour changes:

- `target.ssh.user` defaults to `pbp`. `root` is rejected by config validation.
- The node needs `/etc/pbp/node.yaml` (`vmid_range`, `bridge`, optional `request_timeout`, default 15m). `pbp check` and preflight fail if it differs from `target.vmid_range` and `target.bridge`.
- The daemon and the helper must share major.minor (`0.2.x` with `0.2.y`). A `dev` build is compatible only with a `dev` build.
- A Docker build without `--build-arg VERSION` (including `docker compose build`) is stamped from the new top-level `VERSION` file instead of `dev`. The release workflow fails a tag whose version disagrees with it.
- PBP no longer installs the notification templates itself. Run `pbp node install-templates` as root on the node; preflight only checks them.
- `pbp check` has new steps: node helper version, config, `request_timeout` and refusal.
- The `.deb` is unchanged for daemon-only hosts (the `pbp` user keeps the `nologin` shell). On a node, `apt purge pbp` deletes the `pbp` user and PBP's access.
- Integration tests use a separate test-only admin key (`PBP_IT_ADMIN_SSH_KEY`); see `test/integration/README.md`.
